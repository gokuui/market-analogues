Precision policy: use float16 where behavior passes, native precision for the reference proof

Decision recorded 19 August 2026 after user review. A twelve-decimal numerical match is not itself financially meaningful. It remains useful as an internal differential-test tolerance because it catches implementation errors. Storage and product behavior are judged separately by retrieval membership, ranking quality, finite-value safety, resource cost and whether pruning remains mathematically safe.

Practical float16 retrieval audit — PASS

Candidate representations were quantized to float16 while each query remained native. Every quantized candidate was then rescored through the complete composite distance and overlap/per-instrument constrained top-20 selection. The comparison covers all 24 Gate 09 cases and all 5,850 stored candidates across NSE/NASDAQ, three lookbacks, historical/current cutoffs, A/B quality and low/middle/high liquidity.

Why the exhaustive authority remains native streaming

  1. Float16 changes the metric. It is an excellent approximate retrieval format on this evidence, but it is not identical: one ranking changed and component drift reached 0.0247.
  2. Quantized lower bounds are not proven bounds on the native metric. Rounding may increase a value. Using that value to stop native search could incorrectly prune a true neighbour unless a formal error envelope is subtracted.
  3. The full float16 store still does not fit. Its safety-adjusted projection is 14.98 GB; frontier plus the required 5 GiB reserve raises the requirement to about 20.66 GB, while only about 10.18 GB was free. Even discarding the reserve would still be short.
  4. Streaming removes the incentive. The native T12-02 kernel is already 20.55–29× faster than scalar and uses 374 MB at the full stratified gate, so native reference precision no longer requires a 52.81 GiB store.
